# Pi PR Branch Update

Use only `pi_pr_update_branch` for Git and GitHub mechanics. This route is available for a freshly confirmed merge conflict, or for a base that GitHub reports as behind, which it does only when repository policy requires an up-to-date branch. A behind-only update normally rebases without conflicts.

Call the prompted `rebase` action. If it returns `kind: "stale"`, the run was cancelled before rebase or publication: report the reason and finish without retrying or calling `publish`. The active `/pr` automatically rediscovers the next safe route at settlement, with a bounded attempt count. Otherwise, it fetches the pinned base OID and starts a rebase. If it reports conflicts, call `git_conflict` with `{ "action": "list" }`, then `show` only blocks in the returned paths. During a rebase, `ours` is the pinned base and `theirs` is the replayed PR commit. Never grep for markers or edit marker lines by hand. Resolve the blocks of one file in one `resolve` call (at most 256 blocks; for more, continue with the returned `remaining` blocks) with each block number and id: `@ours`, `@theirs`, `@both` (ours then theirs), or `@base` (diff3 or zdiff3 markers only). For a combined edit, resolve the block to `@both`, then edit the joined lines. If `resolve` reports a changed block, nothing was written: run `list` again. A path with a `note` instead of blocks (binary, deleted, oversized, submodule, symlink, custom merge driver, changed merge attributes, or ambiguous markers) needs a whole-file decision this route cannot make: stop and ask the user, and never pass it to `continue`. Resolve only unambiguous intent, preserving compatible work from both sides. If resolution requires a product, API, data, or migration decision, stop and ask the user; never invent one. Otherwise, give `continue` the complete declared path set. More than one commit may conflict: repeat until verified. A base that only advanced during resolution does not stop `continue` or `publish`. If `continue` returns `kind: "stale"`, other PR authority changed: the helper aborted its unpublished rebase and restored the original head. Report the reason and finish; the active `/pr` rediscovers the next route.

After the helper verifies the rebased branch, run the smallest relevant non-destructive validation. Report failures instead of publishing. Call `publish` once after checks pass. It force-pushes only the verified exact OID with the frozen remote lease; never replay a push whose outcome is uncertain. After a successful publish, the active `/pr` rediscovers fresh GitHub mergeability and feedback for the new head; never infer it from the pre-rebase state.
